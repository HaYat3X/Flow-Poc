# 依頼終了・アーカイブ

project-record-updates.md、cx-context.md、workspace-structure.md、work-close-contract.mdを読む。対象RQの終了条件、すべての関連Workのsynced終了判断・成果・候補同期・残件の行き先、CTの依頼別Plan、CXの案件Context、Knowledge、トレーサビリティ、INの依頼受付・MAT台帳・原本を照合する。未終了Work・未同期候補・行き先のない残件・未達の終了条件があれば完了アーカイブしない。中止は理由と残件の扱いを明示承認する。中止でも関連Workの終了同期と保存・整理は省略しない。

## 最終照合と承認案

Contextを「成果・確定事項」「未反映候補・残件」「進捗・次アクション・サマリ」「参照・トレーサビリティ」の4観点で確認する。MATの反映状態、全Work候補の処理履歴、現在有効なCTX、承認・根拠・反映先を照合し、各観点の反映内容または更新不要理由を終了サマリへ記録する。未確認を反映済みにしない。新たな仕様・方針の判断や未同期候補はClose/Syncへ戻し、アーカイブで補完しない。依頼終了後のCTを根拠にContextの1・12・17・18〜20と分離済み要約の更新要否を確認し、要約・参照の差分を承認案へ含める。

Closeでrequest_closeと判断されたことはアーカイブの自動承認を意味しない。対象・終了状態・理由・原本の移動/残置・受付初期化・CT圧縮・Context差分・更新参照・整理前記録の保存先を示す。承認済みの場合だけ適用する。対象と操作を特定した実行依頼は承認として扱う。承認後は対象を再読し、案から変わっていれば停止する。

## 保存・移動と現行領域の整理

1. 依頼アーカイブフォルダと[終了サマリ](assets/終了サマリ.md)を作る。新規処理はclosure_contract: 1、cleanup_status: pendingを使う。整理前の依頼受付・入力資料一覧・現在地・依頼一覧・Work一覧・更新履歴をバイト列のまま `記録/` に保存する。これは履歴スナップショットであり現行正本ではない。
2. 対象RQのMATと実ファイルを対応付ける。対象依頼専用の受付原本を `input/` へ移す。共有・継続利用中・別依頼用の資料はINに残し、用途と残置理由を記録する。対応不明の資料は黙って移動・削除せず、不足を報告する。終了サマリの「参照移動対応」に原本と整理前記録の保存前SHA256を記録し、保存後と一致することを確認する。残置原本も旧参照と現在の参照先を同じ値で登録する。原本・MAT-IDは削除・再利用しない。
3. CTの依頼本文・対応する進行計画を直下へ、関連終了済みWorkを `work/` へ移す。計画が存在しない中止依頼に計画を新規作成しない。全移動の旧参照→移動先を終了サマリへ登録し、RQのplan_fileと本文・通常の索引/参照を整合する。過去終了判断・承認封印・承認用差分は書き換えない。これらに残る旧パスは移動対応から追跡する。
4. 受付フォームのregistered_request_idが対象RQなら、保存後に固定見出しを残して本文を空にし、record_status: empty、registered_request_id: noneへ戻す。旧受付に属性がなければ依頼名・原本・内容から対象を確認し、判別できなければ初期化を保留する。別依頼の下書きは残す。project_id・案件識別情報・実際の更新者/日時は維持し、TBDの未登録テンプレートへ戻さない。
5. MAT台帳は配置先を更新し、終了資料もID・版を特定できる所在・反映先を維持する。台帳全体を空にしない。Work一覧は現行領域のWorkだけとし、対象RQのアーカイブ済みWork行を除去する。依頼一覧は状態archived・完了日・依頼本文の移動先を持つ1行へ圧縮し、完了/中止の区別は終了サマリのfinal_statusに保持する。
6. 現在地を残る依頼・Workから再構成し、終了対象の現在Work・判断待ち・阻害要因・未同期候補・次アクションを除去する。引継いだ残件は新しい対象IDで残す。主対象・進行件数・総合状態・次アクションも更新する。進行依頼がなければ「進行中依頼なし・次の依頼受付」とし、案件自体を未初期化へ戻さない。
7. 更新履歴は保存済みの対象RQ専用の過去行を、終了結果・終了サマリ・整理前履歴への参照を持つ終了行へ圧縮する。他依頼に関係する行・案件共通行は残す。Contextの承認済み要約/参照差分、Context一覧・トレーサビリティ・関連参照を同じ変更単位で整合し、旧パス→移動先を追跡可能にする。案件共通Context、Product、Knowledgeは移動・初期化しない。

## 検査と報告

終了サマリに承認者/日時、全4観点のContext確認、入力の移動・残置・初期化、CT4台帳の圧縮結果、残件の行き先を記録する。保存・整理が揃ったら `project_workflow_check.py verify-request-close --root . --request RQ-xxxx` で対象依頼のアーカイブ・終了サマリ・関連Workだけを検査する。成功したらcleanup_status: completedにし、失敗したらpendingのまま未完了として不足を報告する。その後、共通strict検査を1回実行する。対象依頼以外の既存エラーはcompletedを妨げないが、終了サマリの検査結果と報告で対象依頼のエラーと区別して記録する。pendingは共通検査では注意として表示される。検査は構造・ハッシュ・参照・残留を扱い、仕様や受入の意味判断は代替しない。成功時は実行コマンドと結果を残し、終了状態・移動先・残置資料・Context確認・管理文書整理・残件・検査結果を報告する。

過去サマリへclosure_contractを自動追記しない。既存アーカイブを整理する場合は、その対象・差分の別承認を得て過去記録を保存する。同じ依頼が整理済みでstrict検査も成功する再実行では、移動・再圧縮・ID発行を繰り返さず適用済みと報告する。
