# 依頼進行計画

project-record-updates.md、cx-context.md、workspace-structure.mdを読み、CTの対象RQ・既存Plan、CXの関連案件Context、現在地、Work一覧、前Workの終了判断・引継ぎを確認する。

## 計画案

- 計画は2つのファイルで持つ。[WBS](assets/WBS.md)は依頼の終了までを見渡す長期の地図、[進行計画](assets/進行計画.md)は次の区切り（判断ゲート・打ち合わせ）までの段取り。全部を初回に詳細化する必要はない。
- WBSは作業パッケージ（成果物が1つ決まる単位、複数のWorkを束ねてよい）の表で、各行にP-ID、親項目ID、成果物、完了条件、開始・終了予定、先行、日付の確度（確定／仮）、状態、紐づくWorkを記す。先の工程は粗い行で残し、根拠のない日付は「仮」とする。P-IDは振り直さない。番号型のWBS IDは作らない。
- ガントはWBSの表から `project_workflow_check.py gantt --root . --wbs <WBS> --write` で生成し、手で書かない。
- 進行計画には今回の区切り、進めるP-ID、今回始めるWorkの表（順番、Work、P-ID、担当、予定、開始条件、完了条件、状態、Work ID）を記す。W-IDはWork開始時に発行し、それまでは「未発行」とする。
- 未確定項目は「未定」とし、根拠なく担当・日付を約束しない。依存関係と日程の矛盾を確認する。旧形式（1ファイルのWBS表・Work候補表）の計画を移行する場合はP-ID・W-ID・完了結果を維持し、移行と状態の対応を承認案に含める。既存の予定を無断で変更しない。
- 承認は2種類。WBSの作業パッケージの追加・削除や成果物・完了条件・時期の変更を含む場合は「Plan承認」、進行計画だけの書き直し（次の区切りの計画、Workの範囲・順番・予定の変更）は「区切り承認」とする。区切り承認は進行計画の差分だけを示せばよいが、Context差分または更新不要理由の確認は省略しない。どちらもplan_revisionを1つ進め、進行計画の改訂履歴に種別・承認者・変更内容を残す。
- 提供された回答・前提・未解決事項を開始条件に照合し、計画に必要な確認事項・影響・確認先を記す。Flow外の課題管理票の登録・更新・状態照合は行わない。
- マイルストーン・判断ゲート、確認が必要な事項、仕様・方針の確認タイミング、次の着手項目を示す。終了条件に寄与しない作業、根拠のないスコープを確定しない。
- 初回/拡張/再計画の別と、計画から明らかになった案件Contextの目的・前提・制約・方針・リスク・未確認事項等の具体差分を毎回示す。対象CTX・現在値・変更案・確度・適用範囲・根拠を承認案に含め、差分がなければ更新不要理由を記す。案の段階で承認済みの現在値を上書きしない。
- Contextの基本情報・進捗・次アクション・3分サマリと分離済み部分の要約も更新要否を確認する。計画の短い要約には参照元・対象ID・同期時点を付け、個々の候補・担当・TODOを複製しない。反映後の文字数超過が見込まれる場合は、cx-context.mdの詳細分離とメイン要約・参照修正も承認案に含める。

## 承認後

[WBS](assets/WBS.md)と[進行計画](assets/進行計画.md)を使い `02_CT_管理/進行計画/RQ-xxxx_WBS.md` と `02_CT_管理/進行計画/RQ-xxxx_進行計画.md` を作成・更新し、ganttコマンドでWBSのガントを生成する。進行計画のwbs_fileとWBSのplan_revisionを揃える。承認対象に含まれるContext差分だけを同時反映し、同一意味の既存CTXは更新する。RQのplanning_statusとplan_file、計画状態、現在地・更新履歴・Context差分・索引/トレーサビリティを同じ変更単位で整合する。更新履歴にはContextの反映内容または更新不要理由を残し、RQ-IDとPlan改訂・根拠を追跡する。計画本文をRQや案件Context本文へ複製せず、Work候補・順序・担当・進捗は計画の正本に保持する。

計画承認はplanning_status: approved。区切りの途中でもapprovedのまま実行できる。区切りの書き直し・WBSの拡張では完了済みP-ID/W-IDと既存判断を消さない。進行計画から完了・中止の行を消してよいが、WBSの紐づくWorkとWorkの作業内容には対応を残す。前提変更による再計画の場合だけneeds_revisionにし、承認後approvedへ戻す。Unknown・conflictのCTXでresolution_task_refが「未割当（Plan）」のものは、計画承認時に解消する計画項目（例 `RQ-0001#P-003`）を割り当てる。

通常のWork後レビューはCloseの終了判断に含まれる。区切りのWorkをすべて消化してもRQの終了条件が未達なら、plan_remainingとして次の区切りを計画する（区切り承認）。区切りの結果で前提・範囲・期限が変わった場合はreplanとしてWBSを直す（Plan承認）。Work開始や依頼終了は自動実行せず、承認済みの次操作を案内する。共通検査を実行する。

Context差分は20セクションのテンプレートに沿った自然言語で提示する。内容・理由・影響を本文で説明し、追跡用ID・確度・承認・根拠は補足属性に置く。管理番号と属性表だけの本文へ変換しない。
