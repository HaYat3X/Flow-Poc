# 依頼進行計画

project-record-updates.md、cx-context.md、workspace-structure.mdを読み、CTの対象RQ・既存Plan、CXの関連案件Context、現在地、Work一覧、前Workの終了判断・引継ぎを確認する。

## 計画案

- 依頼全体の到達点・終了条件と今回具体化する範囲を分ける。全部を初回に詳細化する必要はない。
- plan_coverageはpartial/full。partialでは未計画範囲と具体化条件・必要な情報を必ず残す。範囲自体を特定できない場合は何を確認して洗い出すかを記載する。
- WBSは1つの表で管理し、各行にPlan内一意のP-ID、親項目ID、作業・成果物、担当、開始・終了予定、先行項目ID・開始条件、完了条件、状態、Work IDを記す。別のWork候補表やWBS IDは作らない。W-IDはWork開始時に発行する。
- 未計画工程は粗い親行と具体化条件で残す。作業開始する単位まで分解した行をWorkに対応させる。未確定項目は「未定」とし、根拠なく担当・日付を約束しない。依存関係と日程の矛盾を確認する。
- 状態は「未着手」「進行中」「保留」「完了」「中止」。旧計画を移行する場合はP-ID・W-ID・完了結果を維持し、移行と状態の対応を承認案に含める。既存の予定を無断で変更しない。
- 提供された回答・前提・未解決事項を開始条件に照合し、計画に必要な確認事項・影響・確認先を記す。Flow外の課題管理票の登録・更新・状態照合は行わない。
- マイルストーン・判断ゲート、確認が必要な事項、仕様・方針の確認タイミング、次の着手項目を示す。終了条件に寄与しない作業、根拠のないスコープを確定しない。
- 初回/拡張/再計画の別と、計画から明らかになった案件Contextの目的・前提・制約・方針・リスク・未確認事項等の具体差分を毎回示す。対象CTX・現在値・変更案・確度・適用範囲・根拠を承認案に含め、差分がなければ更新不要理由を記す。案の段階で承認済みの現在値を上書きしない。
- Contextの基本情報・進捗・次アクション・3分サマリと分離済み部分の要約も更新要否を確認する。計画の短い要約には参照元・対象ID・同期時点を付け、個々の候補・担当・TODOを複製しない。反映後の文字数超過が見込まれる場合は、cx-context.mdの詳細分離とメイン要約・参照修正も承認案に含める。

## 承認後

[進行計画](assets/進行計画.md)を使い `02_CT_管理/進行計画/RQ-xxxx_進行計画.md` を作成・更新する。承認対象に含まれるContext差分だけを同時反映し、同一意味の既存CTXは更新する。RQのplanning_statusとplan_file、計画状態、現在地・更新履歴・Context差分・索引/トレーサビリティを同じ変更単位で整合する。更新履歴にはContextの反映内容または更新不要理由を残し、RQ-IDとPlan改訂・根拠を追跡する。計画本文をRQや案件Context本文へ複製せず、Work候補・順序・担当・進捗は計画の正本に保持する。

計画承認はplanning_status: approved。承認済み部分計画でもapprovedのまま実行できる。拡張/再計画では同じ計画の改訂番号と履歴を更新し、完了済みP-ID/W-IDと既存判断を消さない。未計画範囲を具体化した分だけ減らす。拡張の承認前には元の承認済み範囲を失効させない。前提変更による再計画の場合だけneeds_revisionにし、承認後approvedへ戻す。

通常のWork後レビューはCloseの終了判断に含まれる。計画済みWorkをすべて消化してもRQの終了条件が未達なら、plan_remainingとして残りを計画する。Work開始や依頼終了は自動実行せず、承認済みの次操作を案内する。共通検査を実行する。

Context差分は20セクションのテンプレートに沿った自然言語で提示する。内容・理由・影響を本文で説明し、追跡用ID・確度・承認・根拠は補足属性に置く。管理番号と属性表だけの本文へ変換しない。
