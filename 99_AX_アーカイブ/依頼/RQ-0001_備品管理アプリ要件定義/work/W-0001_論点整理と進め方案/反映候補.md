# 反映候補

Workで得た知識と変更案を、読む人が内容と理由を判断できる文章で記録する。候補は承認済みの正本ではない。候補ごとに `### 変更内容がわかるタイトル (候補ID)` を置き、現在の内容、変更案、理由、影響、根拠を説明する。候補本文と処理履歴は追記し、改訂は元候補IDを参照した別候補として残す。採否はWork途中の明示判断またはClose、承認済み反映はSyncで行う。

候補がない節は「なし」とする。下の記入例は書式説明であり、実際の候補ではない。元TODOの作業メモにも候補IDを残す。補足項目の名前を維持し、長い内容は同名の `#### 項目名` の下に複数段落で書いてよい。

## Context候補

### Excel台帳のデータクレンジング担当を未確認事項として追跡する (C-CTX-001)

#### 現在値

データクレンジングの担当が決まっていないことは、プロジェクトコンテキスト7「データに関する注意事項」に文章で書かれているだけで、解消する作業・期限・影響を持つ項目になっていない。

#### 変更案

「Excel台帳の移行時のデータクレンジング担当が未確定」を未確認事項（unknown）として追加する。現行台帳は実物との一致が7〜8割で番号重複もあり、誰がいつクレンジングするかで移行の段取りと費用が変わる。第2回打ち合わせ以降の確認項目一覧 No.12で確認する。

#### 補足項目

- 元TODO・作業メモ: T-002 / 作業メモ.md#TODO T-002
- 候補種別: unknown
- 変更種別: 追加
- 対象CTX: 新規
- 適用範囲: project
- 状態: candidate
- 根拠: MAT-0001「未決事項・確認事項」No.9、「システム・環境に関する情報」
- 反映先セクション: -

候補種別と反映先はContext Policyに従う。変更種別は追加・変更・廃止、対象CTXは新規またはCTX-ID、状態はconfirmed・candidate・unknown・conflictを使う。既定先は `-`、明示先は許可された2桁番号とする。変更・廃止は現在の配置を維持し、移動時は理由を承認案に含める。

```markdown
### 利用者確認の仕様を追加する (C-CTX-xxx)

#### 現在値

現在は利用者の確認方法が未確定である。

#### 変更案

貸出時に利用者を確認し、返却先を追跡できるようにする。

変更の理由・影響を、判断に必要な詳しさで説明する。

#### 補足項目

- 元TODO・作業メモ: T-xxx / 作業メモ.md#該当TODO
- 候補種別: requirement
- 変更種別: 追加
- 対象CTX: 新規
- 適用範囲: project
- 状態: candidate
- 根拠: 元資料のID・版・該当箇所
- 反映先セクション: -
```

## 意思決定候補

なし。

人が実際に決定した事実だけを記録する。AIの提案・暫定判断は含めない。

```markdown
### 採用した方針と理由 (C-DEC-xxx)

#### 決定事項

何を採用し、なぜその判断に至ったかを記載する。

変更の理由・影響を、判断に必要な詳しさで説明する。

#### 補足項目

- 元TODO・作業メモ: T-xxx / 作業メモ.md#該当TODO
- 決定者: 実際の判断者
- 決定日: YYYY-MM-DD
- 根拠: 決定を確認できる資料・記録
- 影響範囲: 影響する業務・機能
- 適用条件: この判断が有効な条件
```

## リスク・課題候補

なし。

課題・リスク・QAの対応管理はFlow外で行う。外部管理票の担当・期限・対応状態を複製せず、案件への影響だけを残す。外部管理票の登録・更新は行わない。

```markdown
### 案件への影響がわかるタイトル (C-RSK-xxx または C-ISS-xxx)

#### 内容

起こり得る事象、または発生済みの事象を説明する。

変更の理由・影響を、判断に必要な詳しさで説明する。

#### 補足項目

- 元TODO・作業メモ: T-xxx / 作業メモ.md#該当TODO
- 種別: risk または issue
- 原因・発生条件: 原因または発生条件
- 影響: 案件の前提・制約・方針への影響
- 可能性・緊急度: 判断と理由。未確認ならunknown
- 対応案: 必要な対応・確認
- 担当・期限候補: Flow外の管理先を参照。未確認ならunknown
- 根拠: 観測した事実・資料
```
