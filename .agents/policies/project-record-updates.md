# プロジェクト記録更新Policy

## 正本と状態

- CTは現在地・依頼一覧・Work一覧・更新履歴の4台帳と、依頼本文・進行計画の正本。CXは育てる案件概要、要求・前提・制約・方針、現在有効な意思決定の正本。
- Contextの属性・承認・適用性・ライフサイクルはcx-context.mdに従う。Work入力の状態confirmed/candidate/unknown/conflictと混同しない。未確認を推測でconfirmedへ変更しない。
- RQ、MAT、W、CTX、分類別Knowledge IDは再利用しない。意思決定はCTXを使う。Flow外の管理票のIDは発行・管理しない。
- 同一情報は正本を1か所に持つ。索引・現在地は状態と参照を持ち、本文を複製しない。
- 課題・リスク・QAの対応管理はFlow外で行い、管理票の作成・登録・更新・同期はFlowの手順に含めない。外部の管理状態をFlow側で判断しない。提供された回答・対応結果が作業や仕様に影響する場合は、根拠として記録し、必要なContext・計画の変更を通常の承認後に反映する。
- 依頼本文は「プロジェクト計画」と呼び、対象システムの目的・範囲・成果物・受入条件・責任者・制約を管理する。RQ-ID・依頼フォルダ・request属性は変えない。進行計画は担当・予定・依存関係・完了条件を1つのWBS表で管理する。別のWork候補表は作らない。Planの予定とWorkの実績を区別する。
- 案件Contextは20セクションで案件の現在の姿を示す。進捗・次アクション・期間はCT・Work、分離済みセクションの詳細は移動先だけを正本とする。メインの該当箇所は参照元・同期時点付きの要約であり、独立して状態やTODOを管理しない。

## 入力とWork開始

- 受付原本はINの入力とMAT台帳、Work開始後の直接受領原本は対象Workの入力とWI台帳で追跡する。同じ資料を別Workで使う際は元ID・版・時点を参照する。
- 原本を編集・上書き・削除しない。改訂版は別ファイルで保存する。配置修正は承認された移動先と参照を同じ変更単位で更新する。
- 開始時に関連Context・依頼・Plan・前Work引継ぎ・Knowledge・Productから必要事項だけを `入力/Work入力.md` 1枚に要約する。根拠・版・確度・対象外を残し、承認された入力ベースラインを固定する。
- 入力一覧に要約と詳細参照をWI-IDで登録する。取込方式はcopy/snapshot/reference。要約はsnapshot、元資料は原則reference。版固定できない資料のみ複製する。
- 直接受領原本は元欄に入手元・確認日・元資料名、配置先に実ファイルのルート相対パスを記録する。追加・差替えは新規WI行または明示状態変更とし、理由・影響を作業メモに追記する。要約の旧版を黙って上書きしない。
- Work入力にない資料を暗黙に使わない。追加が必要なら入力同期で登録する。成果物は同一Workの入力へ二重登録しない。

## 作業記録と候補

- 作業内容は目的・期待する価値、対象・対象外、入力資料、完了条件・確認方法、関連作業の正本とする。TODO・進捗・確認待ち・実施結果は記載しない。要求上の期限や品質制約と、実行担当・作業予定を区別する。
- 実行計画とTODO状態の正本は作業メモのTODO一覧とする。現在の計画は更新し、追加・分割・変更・中止の理由と影響は日付付き作業記録に追記する。日付付き記録は削除・上書きしない。
- 目的・対象範囲・完了条件を変える場合は、実行計画の調整と区別して変更案を提示し、利用者またはPMの承認後に作業内容と関連RQ・Plan・Contextを必要に応じて整合させる。TODO変更だけで要求や品質基準を変更しない。
- TODOを扱う前に作業内容・Work入力/入力一覧・作業メモ・反映候補を読む。対象Work/TODOを特定する。
- 判断・前提・リスク・成果・次の対応が変わったとき、および最終報告前に、日付付きで実施・観測事実・解釈・根拠・未解決・次対応を該当TODOへ追記する。作業メモ内のTODO状態も整合させ、成果の配置先とWork全体の完了条件の確認結果・根拠を残す。
- 会話や記憶だけで後から再構成しない。記録漏れはファイル・差分・ログを根拠に補い、不明はunknownとする。
- Contextと反映候補の本文は自然言語で内容・理由・影響を説明する。テンプレートの見出しを維持し、追跡用ID・確度・承認・根拠は補足箇条書きに置く。比較用の表・索引・処理履歴と、旧書式の互換読取は維持する。
- Context・意思決定・Knowledge・Productの候補があればWork内一意の候補ID・元TODO・根拠を反映候補へ記録し、作業メモから参照する。残った問題・確認待ちは未解決事項に影響・次の対応・引継ぎ先を記録する。Flow外の管理票への登録・更新は候補に含めない。
- 意思決定は人の決定事実、リスクは将来の不確実な事象、課題は発生済み事象。影響・根拠・対応を保持する。Knowledgeは再利用可能な適用条件・手順/基準・例外・限界を持つものだけを候補にする。

## 承認と更新

- 読取りと具体的な変更案の作成は進めてよい。正式なContext・Knowledge反映、終了、アーカイブは対象・操作・状態遷移・根拠を提示して承認を得る。
- 対象と操作を特定した実行依頼は承認として扱い、同じ内容を再承認させない。承認後に差分が生じた場合だけ適用を止めて変更案を更新する。
- 初回受付では案件Contextの最小核を初期化する。依頼・Planの作成・改訂では、目的・要求・対象範囲・受入条件・前提・制約・方針・リスク等のContext差分を根拠付きで提示し、承認対象に含まれる差分をCTの正本と同じ変更単位で反映する。案の段階で現在値を上書きしない。
- Context差分がなければ更新不要理由を更新履歴に記録し、本文やupdated_atだけの更新を強制しない。RQ本文、個々のWork候補・順序・実行担当・進捗はCXへ複製せず、CTXの根拠とトレーサビリティから元のRQ・Plan改訂を追跡する。Plan承認では部分/全体の範囲と未計画範囲も保存する。案件体制・判断権限はCX、実行担当はCT・Workと区別する。
- CloseとSyncの境界、承認対象の保存、部分計画の継続案内はwork-close-contract.mdを正本とする。Closeが判断、Syncが適用と終了確定を担当する。途中同期はWorkを閉じない。
- Skill選択は業務承認を意味しない。Closeは承認後に終了同期の対象と依頼文を案内して停止する。ただし利用者がClose→Sync一括を依頼済みなら承認された範囲で続けてよい。
- 更新では一覧・実体・frontmatter・本文・関連ID・参照パス・更新履歴を同じ変更単位で整合させる。updated_at/updated_byは実際の更新に合わせる。
- Contextの更新不要ならCloseに理由を残す。更新対象があればSyncで同一意味の既存CTXを更新し、一覧とトレーサビリティを更新する。
- 既存の受付・依頼改訂・Plan承認・承認済み途中Sync・終了同期で、Contextの基本情報・進捗・次アクション・3分サマリも更新要否を確認する。要約は対象ID・参照元・同期時点を残す。終了同期の要約と必要な詳細分離はCloseの承認用targetに含め、Syncで判断を増やさない。
- 関連ファイルを同じ変更単位で更新し終えてから、AGENTS.mdの実行頻度に従って共通検査を1回実行し、更新内容・検査結果・残件を報告する。個別ファイルの更新途中では実行しない。推測で検査エラーを修正しない。

## 依頼終了後の保存と現行領域の整理

- 依頼終了はアーカイブ移動だけでなく、Context最終確認・入力初期化・CT圧縮までを承認対象とする。新規の終了サマリはclosure_contract: 1とし、完了/中止・承認・残件・保存対応・検査結果を記録する。過去サマリや承認封印を自動変換しない。
- Contextの成果・確定事項、未反映候補・残件、進捗/次アクション/サマリ、参照/トレーサビリティを最終照合し、各観点の反映内容または更新不要理由と根拠を記録する。新たな判断や未同期候補はClose/Syncへ戻す。依頼終了後のCTに基づく要約・参照更新は終了承認に含めて適用する。
- 初期化・圧縮前に依頼受付・MAT台帳・CT4台帳を対象依頼AXの記録/へバイト列のまま保存する。保存前SHA256と保存先を終了サマリに記録する。対象依頼専用の受付原本はAXのinput/へ移動し、共有・継続利用資料は理由付きでINに残す。原本は削除せず、保存前後のSHA256を照合する。
- 受付フォームはregistered_request_idで対象を識別し、登録時に内容を残す場合はRQ-IDを記録する。対象依頼の受付だけを保存後にempty/registered_request_id: noneへ戻す。別依頼の下書きは維持する。旧受付の帰属が不明なら推測で初期化しない。
- MAT台帳は削除・空初期化せず、終了資料のID・所在・反映状態/先を含む索引を保持する。過去Workもこの索引を参照する。発行済みIDと案件識別情報・実際の更新情報を維持する。
- Work一覧は現行領域に残るWorkのみ掲載し、終了依頼のアーカイブ済み行を除去する。依頼一覧はarchived・完了日・依頼本文のアーカイブ先を持つ1行を維持する。現在地は残る依頼/Workから再構成し、引継いだ残件を新しい対象IDへ付け替える。進行依頼ゼロでも案件の識別情報やContextを未登録状態に戻さない。
- 更新履歴の対象RQ専用の過去行は保存後に終了サマリ・保存済み履歴への終了索引へ圧縮できる。他依頼・案件共通の履歴は維持し、日付付きWork記録や封印は圧縮しない。移動対応は終了サマリ・トレーサビリティ・更新履歴から追跡可能にする。
- 対象依頼に限定した検査（`verify-request-close`）で保存・ハッシュ・索引・現行領域の残留を確認する。失敗時はcleanup_status: pendingで未完了として報告し、成功時だけcompletedにする。続けて共通strict検査を実行し、対象依頼以外の既存エラーは区別して記録する（completedを妨げない）。再実行で整理済みなら再移動・再圧縮しない。
