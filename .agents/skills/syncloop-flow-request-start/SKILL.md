# 依頼受付・登録

project-record-updates.md、cx-context.md、workspace-structure.mdを読み、INの依頼受付、CTの依頼・計画、CXの案件Context、現在地・依頼一覧・入力資料一覧を確認する。新規登録ではアーカイブを含む既存IDから未使用RQ/MATを選び、改訂では対象RQを維持する。

受付の固定見出しと見出し外の追記を確認済み・仮定・未確認・矛盾に分け、RQ名・種別・Lifecycle開始地点・期待結果/終了条件・対象/対象外・関連契約/依頼/Context/原本を提示する。重複依頼や重大な矛盾は登録せず不足を示す。受付と原本が食い違う場合、事実は原本、依頼の意図（何をしてほしいか・期限・判断者）は受付を正とし、食い違いを矛盾として判断が要る点に出す。受付が原本の転記になっていても、原本を根拠に読む。

種別（request_type）は依頼の性質、Lifecycle開始地点（lifecycle_start）はどの工程から始めるかで、別の軸として次から選ぶ。どちらも依頼一覧の同じ列と一致させる。

| 項目 | 選択肢 |
| --- | --- |
| request_type | `new_development`（新規開発）、`enhancement`（改修・機能追加）、`investigation`（調査・検証）、`estimate`（提案・見積）、`maintenance`（保守・運用対応）、`other`（理由をプロジェクト計画の背景に書く） |
| lifecycle_start | 提案・見積、契約前、要件定義、基本設計、詳細設計、実装、テスト、移行、保守（案件Contextの現在フェーズと同じ語彙） |

案件IDは初回登録で決め、以後変えない。`project_id` は `PRJ-` と英大文字・数字・ハイフン（例 `PRJ-MINATO-ASSET`）、`flow_project_id` は `flow-` と初回登録の年4桁、`-` と英小文字・数字・ハイフン（例 `flow-2026-minato-asset`）とする。選択肢・書式に合わない値は共通検査がエラーにする。

登録する文書の名称は「プロジェクト計画」とし、対象システムの目的、成果物ごとの受入条件・確認方法・判断者、プロジェクト責任者・関係者、制約・要求期限、案件共通事項の参照を整理する。本文の未確定項目は「未定」とし、納期・担当・予算を推測で約束しない。詳細日程・作業分解は進行計画に委ねる。管理上のRQ-ID・request属性・依頼フォルダは維持する。

受付時の確認事項・影響・確認先はプロジェクト計画の未確認事項欄に記す。課題・リスク・QAの対応管理はFlow外とし、管理票の作成・登録・初期化は行わない。提供された回答から要求・仕様・方針が確定した場合は、通常のContext差分として扱う。

初回案には案件ID・安定したflow_project_id・案件名と、案件Contextの最小核を含める。目的、ステークホルダー、対象、要求、前提/未確認、受入条件を初期化し、根拠・適用範囲・承認状態を示す。不明はunknown、適用外はreason付きnot_applicableとする。情報が不完全でも状態を区別して概要を育て始める。

Contextは既存の20セクションを使い、全欄の確定を登録条件にしない。要求・前提・仕様・方針・意思決定は型に対応する小見出しの下へCTX項目として置く。外部の課題管理票の担当・期限・対応状態をFlowへ複製しない。基本情報・進捗・次アクション・3分サマリは参照元と同期時点付きで整理し、依頼やTODOの正本にしない。反映後の文字数超過が見込まれる場合は、cx-context.mdの部分分離とメイン要約・参照修正を承認案に含める。

依頼の作成・改訂ごとに、目的・要求・対象/対象外・受入条件・前提/未確認等を既存Contextと照合し、対象CTX・現在値・変更案・確度・適用範囲・根拠を承認案に含める。RQ固有のContextはapplies_toにRQ-IDを記録する。差分がなければ更新不要理由を示す。案の段階で承認済みの現在値を上書きしない。

承認案は依頼セットで出す。「判断が要る点」（RQ名と種別、期待結果・終了条件、対象/対象外、Context差分または更新不要の理由、矛盾・未確認の扱い）と「整合のための変更」（台帳・索引・ID・frontmatterのファイル名だけ）を分け、利用者には前者を読んでもらう。後者の整合は共通検査で確かめる。作業上の前提（working_assumption）を置く場合は、判断点に「案件の判断:」で始まる別の行として示し、承認者が案件の判断も兼ねたことを記録する。

承認案を出した時点で[依頼承認記録](assets/依頼承認記録.md)（`02_CT_管理/依頼/RQ-xxxx_依頼承認記録.md`、初回はテンプレートから作る）に状態「提示中」の見出し（登録承認／改訂承認）を追記し、正本はまだ書かない。承認を得たら承認日時・承認者と立場・承認の発言を記録して「承認済み」にし、更新履歴の根拠に `RQ-xxxx_依頼承認記録#A-xx` を書く。差し戻しは理由を残し、修正案は新しい見出しで出す。

unknown・conflictのContextで解消する作業がまだ決まっていない場合は、resolution_task_refを `未割当（Plan）` とし、Planで計画項目を割り当てる。

承認後は[プロジェクト計画](assets/プロジェクト計画.md)を `02_CT_管理/依頼/RQ-xxxx_プロジェクト計画.md` へ保存する。文書見出しは `RQ-xxxx プロジェクト計画（案件名）` とする。受付原本をINに保持し、MAT台帳とRQ.related_inputsを関連付ける。初回は案件Contextに識別情報と最小核を必ず反映し、管理4台帳・必須文書のproject_idと更新情報を初期化する。追加受付・改訂は承認対象に含まれるContext差分だけをプロジェクト計画の保存と同じ変更単位で反映し、同一意味の既存CTXは更新する。プロジェクト計画の本文・状態・進捗をCXへ複製しない。既存文書は実際の参照先を使い、名称変更だけのために自動改名しない。

新規RQはplanning_status: unplanned、plan_file: noneで開始し、次はPlanを案内する。改訂では既存の状態・関連Work・計画参照を維持し、承認済み計画の前提が変わる場合はRQとPlan双方のplanning_statusをneeds_revisionへ揃えて再計画を案内する。この状態変更も承認案に含め、既存の計画項目・改訂履歴を消さない。依頼一覧・現在地・更新履歴・Context索引/トレーサビリティを整合し、更新履歴にはContextの反映内容または更新不要理由と根拠を残す。計画未承認で空のPlanを作らない。依頼受付の初期化は登録承認に含まれる場合だけ行い、空ならempty/registered_request_id: none、内容を残すならregistered/registered_request_id: 対象RQ-IDへ揃える。別依頼の記入開始時はregistered_request_idをnoneに戻す。共通検査を実行する。Workは作成しない。

Context本文と反映候補はcx-context.mdとテンプレートに沿った自然言語で作成する。内容・理由・影響を本文で説明し、追跡用IDと属性は補足に置く。承認用の反映案も同じ文章形式を維持し、管理番号と横長の表だけの文書に変換しない。
