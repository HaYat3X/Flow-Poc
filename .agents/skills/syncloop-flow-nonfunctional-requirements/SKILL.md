# 非機能要件の初版作成

要件定義で、性能・可用性・セキュリティ・運用・移行・テスト・教育などの非機能要件を、顧客と合意するための**初版（80%）**にまとめるスキルです。目的は、顧客に提示できる形の下書きを速く作り、正式版の作成を楽にすることです。要件の確定、顧客との合意、契約条件の決定は行いません。

入力資料を読み、足りない項目は利用者と対話して補います。入力が具体的で価値が高いほど、そのまま根拠付きで埋まる項目が増えます。入力が少ないときは、値を推測せず、「未確認」と質問が増えます。

## 出力するもの

| 出力 | 内容 |
| --- | --- |
| `非機能要件.md` | 前提と9章（構成、可用性、性能・拡張性、セキュリティ、運用・保守、移行、テスト・受入、教育、確認事項）。標準本文は [非機能要件テンプレート](./assets/非機能要件テンプレート.md) を使う |
| `システム構成図.excalidraw` | 構成データ（JSON）から生成する構成図。VS CodeのExcalidraw拡張やexcalidraw.comで開いて手直しする |
| 構成データ（JSON） | 構成図の元データ。構成を変えるときは、これを直して再生成する |

契約条件（契約不適合責任、保守契約の期間・費用・対象範囲、契約上の検収条件）は書かず、「契約書・受託条件を参照」とだけ記す。PMレイヤの文書（計画書、報告書）は作らない。

## 呼出条件

- このディレクトリは特化Skillの保管用であり、保管中は実行しない。
- 利用者が配置を依頼した場合だけ、ディレクトリ一式を `.agents/skills/` へ配置し、`sync-skills` で `.claude/skills/` にも複製する。
- 配置後も、利用者がその都度 `$syncloop-flow-nonfunctional-requirements`（Claude Code・GitHub Copilotでは `/syncloop-flow-nonfunctional-requirements`）を明示したときだけ実行する。自然言語の類似依頼や他Skillから自動実行しない。
- Skillの実行依頼は、要件の承認・合意やContextの正式化を意味しない。

## 実行ゲート

次の3点を利用者に確認する。いずれかが未指定・不正なら、不足を伝えて止まり、ファイル・フォルダ・ログ・Work記録を作らない。「作って」だけで指定が揃ったとみなさない。

| 必須指定 | 内容 |
| --- | --- |
| 対象Work | 開始済みの要件定義Workの作業フォルダ。カレントディレクトリや直前の会話から選ばない |
| 入力 | 使用する資料のパスまたはID。対象Workの入力一覧に登録されたものだけを使う。会話で出た条件は、利用者が入力として指定し、入力一覧に登録してから使う |
| 出力 | 対象Work内の出力フォルダ。Work外には出さない |

対象Workの `作業内容.md`、`入力/入力一覧.md`、`作業メモ.md`、`反映候補.md` を読む。更新の場合は、既存の `非機能要件.md` と構成データも読む。

## 手順

1. **入力の棚卸し**: 章ごとに「入力から埋まった項目」「入力が薄い項目」「入力がない項目」を一覧にして利用者に見せる。
2. **質問**: 薄い・ない項目を、章単位でまとめて質問する。一度に全章は聞かない。回答が「まだ決まっていない」なら、そのまま「未確認」にして次へ進む。質問には [観点カタログ](./references/観点カタログ.md) から質問と「よくある値」の例を添える。例は選択肢として示すだけで、回答を得るまで本文に入れない。
3. **反映**: 回答を本文に反映し、その章の状態（確認済み・未確認・対象外の件数）を見せる。
4. **構成図**: 構成の情報が揃ったら、構成データを作り、利用者に構成要素・つながりを確認してから生成する（下記）。
5. **初版**: 利用者が区切ると決めたら、未確認の項目を「9. 確認事項」にまとめて出力する。出力前に、更新するもの（Work内の `非機能要件.md`、`システム構成図.excalidraw`、構成データ）と、更新しないもの（入力の原本、契約・受託条件、Context）を提示し、出力先の了承を得る。
6. 作業メモに、入力資料、未確認の件数、確認事項、検査結果を追記する。Contextへの反映は反映候補に載せ、Close → Sync に渡す。

## 項目の書き方

各項目は「項目・要件・担当・状態・根拠」の表で書く。

| 列 | 内容 |
| --- | --- |
| 項目 | 例: セッションタイムアウト |
| 要件 | 例: 15分。測れる値（数値・期間・条件）で書く |
| 担当 | 自社 / 顧客 / 共同。担当が値の中に埋もれないよう、この列に分ける |
| 状態 | 確認済み / 未確認 / 対象外 |
| 根拠 | 入力資料と箇所。対象外のときは理由 |

- 入力に根拠がない値を「確認済み」にしない。観点カタログの例や一般的な値を、回答なしで要件欄に入れない。
- 「業務に問題がない程度」のような測れない目標は、そのまま確定せず、測り方の案を添えて確認事項に出す。
- 「のちほど相談」「[ ]件」のような未確定は、要件欄に値として書かず、状態を「未確認」にして確認事項へ移す。
- 対象外にした項目は、理由を根拠に書く（例: インターネット非公開のため第三者検証は実施しない）。
- 入力同士が矛盾するときは、どちらも採用せず、双方の根拠を示して確認事項にする。

## 構成図の作り方

構成図は構成データ（JSON）から生成する。座標はスクリプトが決めるので、構成データには**配置のマス（col・row）**を指定する。項目と許可値は [構成データ.schema.json](references/構成データ.schema.json) を参照する。

- `zones`: 囲み枠。`kind` は network / server / external。`parent` で入れ子にできる。
- `nodes`: 構成要素。`zone`、`kind`（client / boundary / app / data / external）、`status`（確認済み / 未確認）、`col`、`row`、`label`（改行は `\n`）を持つ。未確認の要素は、点線・黄色・「（未確認）」付きで描かれる。
- `links`: つながり。`from`、`to`、任意で `label`、`style`（solid / dashed）、`route`（auto / bottom）。
- 配置の目安: 左から右へ「利用者 → 境界（FW・ネットワーク）→ サーバ → 外部」。DBやログはサーバの下の行。同じゾーンの要素は隣り合うマスに置く。
- ラベルを付けられるのは、同じ行または同じ列の直線のリンクだけ。折れ線になるリンクの説明は、構成要素のラベルに書く。
- 図の全体を回り込ませたいリンク（例: 外部からの保守接続）は `route: bottom` にする。

```powershell
py -3 scripts/architecture_excalidraw.py validate --data <構成データ.json>
py -3 scripts/architecture_excalidraw.py render --data <構成データ.json> --output <Workフォルダ>/システム構成図.excalidraw
```

`render` は既存ファイルを上書きしない。再生成すると Excalidraw 上の手直しは失われるため、差分を確認して利用者の判断を得る。例は `examples/sample-system/` にある。

## 品質と停止条件

- 対象Work、入力、出力先のいずれかが未確認なら、作成を止める。
- 根拠のない値で「確認済み」を作らない。構成データの `status` も同じ。
- スクリプトは、ID重複、存在しない参照、同じマスへの重複配置、ゾーン枠への他ゾーン要素の混入、折れ線リンクへのラベル、既存ファイルの上書きを停止する。
- 初版を最終版・顧客提示可能な完成版として扱わない。顧客の様式への変換、図の見た目の調整、図の画像書き出しは、利用者が必要なときに別途行う。

## 作らないもの

- 契約条件の決定、合意の代行、法的・品質保証の判断
- PMレイヤの文書（計画書、報告書、テスト計画書）
- GIS固有の観点（地図表示の性能、背景地図のライセンス、座標系など）は、観点カタログに含めない。必要なときは、利用者の指示で章に追記する
- 入力の原本、Context、他Skillの出力の変更
