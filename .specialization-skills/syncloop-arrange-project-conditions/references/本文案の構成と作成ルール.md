# 本文案の構成と作成ルール

## 目的

成果物として読める「受託条件明細書（本文案）」を作る。PC-IDごとの状態一覧やレビュー指摘を、そのまま本文の代わりにしない。案件で確認できた内容を自然な業務文書へ編集し、関係者が条件案として検討できる形にする。

## 標準構成

標準出力は [受託条件明細書テンプレート](../assets/受託条件明細書テンプレート.md) の表紙・別表1〜8とする。従来の9分類は抽出・レビューの分類であり、出力の別表構成とは区別する。元Excelの項目構成をMarkdownの見出しと単純な表へ置き換え、会社固有の条文・例示値・説明書の作成指示は本文へ転記しない。

| 別表・小節 | 本文に書く内容 | 表現 |
| --- | --- | --- |
| 表紙 | 文書情報、本件業務の名称・内訳、当事者、別表一覧 | 契約番号は指定入力にある場合のみ記載。社内承認と当事者合意を区別する |
| 別表1: 1.1、1.2 | 業務概要・利用範囲、作業概要 | 項目・記入内容表、内訳業務ごとの作業概要表 |
| 別表2: 2.1〜2.5 | 前提資料・条件、ハードウェア／ネットワーク構成、システム条件、貸与ドキュメント | 版を特定した資料表、主体・期限付き条件表、構成・製品表、資料の貸与表。変更手順は2.2に記載 |
| 別表3: 3.1、3.2 | 対象業務・対象外、他システムとの関連、対象工程 | 対象境界表、入出力・連携表、工程別の作業内容表 |
| 別表4: 4.1〜4.3 | 全体スケジュール、役割分担、詳細作業スケジュール | 工程・節目の日程表、主担当と双方の作業内容を分けた表。詳細日程は必要時のみ版固定参照 |
| 別表5: 5.1、5.2 | 納入物品・検収基準、受託側から委託側への貸出物 | 内訳業務・数量・媒体・納入日・検収日付き一覧、検査方法・判断者・条件表、貸出表 |
| 別表6: 6.1、6.2 | プロジェクトリーダー・推進体制、会議体・運営方法 | 主体・役割・権限・対応先を明示した体制表、会議表 |
| 別表7: 7.1〜7.3 | 作業実施場所、貸与設備・ソフトウェア、その他作業環境 | 所在地・場所・期間・使用条件表、設備貸与表、アクセス・情報保護等の条件表 |
| 別表8 | 個別開発機能一覧 | No.・業務・画面・帳票・機能概要・対象区分の一覧 |

案件に応じて保守・運用、利用権限などの別表を追加する。利用者が別様式を明示した場合は指定を優先し、標準項目との対応をレビューに残す。甲乙、契約番号、署名・押印欄は必須にしない。内製では文書名、当事者名、納入・検収を作業条件・関係部門・引渡し・完了確認などへ読み替える。

## テンプレートの記入方法

- テンプレート全体を読み、標準の見出し順と記入表を使う。`{{...}}` は記入案内であり、実際の案件の値または状態表示へ置き換える。雛形のまま保存して完了としない。
- 一覧は案件に含まれる資料・条件・工程・作業・納入物品・機能ごとに行を増やす。工程名は表紙、1.2、3.2、4.1、4.2、5.1で一致させる。
- 不足は `未確定（OI-xxx）`、競合は `要協議（OI-xxx）: 資料Aの値 / 資料Bの値`、提案は `候補・未採用（OI-xxx）: 案の内容` と該当セルへ書く。OI-IDは実際のレビューと対応させる。確認できた値まで未確定へ置き換えない。
- 「なし」「対象外」「適用不要」は指定入力で確認できた場合だけ使用し、理由を本文、根拠をレビューへ記載する。資料がないだけでは「なし」にしない。画面・帳票が不要な機能でも、確認できなければ空欄や「-」で済ませない。
- 対象外の小節も見出しを残し、表の代わりに理由を書くことができる。4.3は詳細日程の採用有無・理由を記載し、入力にない詳細計画を作らない。別表8は個別開発がないことを確認できた場合だけ省略でき、その理由と省略した旨を表紙の別表一覧とレビューへ残す。残る別表の番号は変えない。
- 図や線表がなくても、2.3の構成要素・接続先・対象動作範囲、3.1の入出力・対象境界、4.1の日程、6.1の組織・役割の対応を表で記載する。入力図を参照する場合も、本文の対象範囲を参照だけで済ませない。
- 2.5の委託側からの資料貸与、5.2の受託側からの物品貸出、7.2の委託側からの設備・ソフトウェア貸与を混同しない。数量、期間、返却・廃棄、費用・利用条件は根拠がある値だけ記入する。
- Markdown表はセル結合を使わず、各行に工程名・主体などを繰り返す。セル内の複数項目は `<br>` で区切り、文字としての縦棒は `&#124;` にする。色・網掛けの代わりに対象区分と状態を文字で示す。

## 作文と確度のルール

- 全体を「本文案」「未合意」などで識別し、本文が整っていることを正式な合意・提出可の証拠にしない。
- 資料で確認できる業務・機能・数量・日付・主体は具体的に書く。すべてを「別途協議」で済ませない。
- 既知の条件は文章や表にまとめ、本文へ確認者・状態・根拠の列を過剰に並べない。詳細な根拠・指摘・採否はレビューへ分ける。
- 不足は該当箇所で「未確定」とする。競合は「要協議」とし、採否が必要な選択肢・日付を並記する。どちらかを選んで文章を完成させない。
- 合理的な候補文は提示できるが、「候補・未採用」と明示し、理由をレビューへ残す。例えば対象機能に基づく受入シナリオの候補は出せるが、試験件数、性能目標、許容不具合数を勝手に決めない。
- 提供期限・修正担当・費用負担・保証・免責・みなし検収・権利帰属などの実質条件を、文書らしくするためだけに追加しない。
- 根拠のない契約成立文、法的優先順位、解除・損害条項、署名済み扱いを挿入しない。本文案の作成は締結用契約書の起草・法的審査ではない。
- 専門確認が必要な点は本文でも未確定とし、レビューへ確認先・影響を記録する。

## 2つの出力の対応

本文の未確定箇所にはOI-IDを添え、レビュー側に「本文の節 -> PC-ID -> 根拠・OI-ID」の対応表を置く。本文へWI-IDや長い競合分析を毎回繰り返す必要はない。

本文案とレビューで、対象、対象外、担当、日付、成果物、完了条件、承認・合意・候補の状態が一致することを確認する。本文だけで新しい候補を追加せず、対応するPC項目にも候補理由・未採用状態を記録する。

利用者が2つを求めた場合、最終報告は本文案の保存先を先に示し、レビューの保存先を次に示す。1ファイル指定の場合は本文案を先、確認事項・レビューを後にする。

## 出力検査

1. 表紙、別表1〜7、各小節、別表8または省略理由が揃い、表紙の別表一覧と一致するか確認する。
2. `{{...}}`、空の記入欄、例示会社名・日付・製品名、説明書の作成指示が残っていないか確認する。
3. 表の各行の列数が見出しと一致し、改行や縦棒で表が崩れていないか確認する。
4. 前提資料の版、対象・対象外、工程名、役割、数量、納入・検収日、検査期間と完了条件が別表間で一致するか確認する。不一致は未確定表示とレビューへ残す。
5. 未確定・競合・候補のOI-IDと、レビューの「別表・小節・行名 -> PC-ID -> 根拠・OI-ID」の対応が揃っているか確認する。
6. 契約成立文、文書の優先順位、署名・押印、免責・費用負担・みなし検収などを様式から自動挿入していないか確認する。
