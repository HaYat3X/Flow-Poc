# 案件の取り決め整理・レビュー

「今回、誰がどこまで、どの条件で実施し、何をもって完了とするか」を項目ベースで整理し、受託条件明細として読める本文案と、確認事項・レビュー結果を作る。要件定義書やプロジェクト計画書の代替ではなく、それらと見積・合意記録などを突き合わせる。

受注側の約束、発注側のベンダー確認、内製の部門間合意に使える。特定会社の様式・工程名・条文に依存させず、法的判断や代理合意は行わない。

## 出力するもの

| 出力 | 内容 |
| --- | --- |
| 受託条件明細書案（Markdown） | Excel様式に相当する表紙・別表1〜8の項目と記入表を揃え、案件の業務概要、前提条件、対象範囲、日程・役割分担、納入物品・検収基準、体制、作業環境、個別開発機能を記入する |
| 確認事項・レビュー結果 | 根拠、項目の状態、入力間の矛盾、不足、未合意事項、確認先・質問、本文案との対応を示す |

標準はこの2つを別ファイルで出す。レビューだけを作って本文案の代わりにしない。利用者がレビューのみなどの限定を明示した場合は指定を優先する。ファイル名は候補を示せるが、保存先・形式を確認する前に作成しない。1ファイルにまとめる指定なら本文案とレビューを別セクションにする。

本文案は締結・提出可能な完成版ではない。未確定箇所や候補文は本文でも識別し、詳細な指摘・根拠はレビューへ分離する。内製では「作業条件・役割分担書（案）」などの適切な文書名へ読み替え、契約番号・甲乙・押印欄を強制しない。

標準本文は [受託条件明細書テンプレート](./assets/受託条件明細書テンプレート.md) を使う。Excelのセル結合や色を再現するのではなく、同じ項目を見出しとMarkdown表で読める明細書にする。9分類の要約やPC-ID一覧だけで代用しない。テンプレートは出力様式であり、案件の事実・標準契約条件の入力ではない。

## 呼出条件

- このディレクトリは特化Skillの保管用であり、保管中は実行しない。
- 利用者が配置を依頼した場合だけ、ディレクトリ一式を `.agents/skills/` へ配置する。
- 配置後も利用者がその都度 `$syncloop-arrange-project-conditions` を明示した場合だけ実行する。自然言語の類似依頼や他Skillから自動実行しない。
- Skillの実行依頼は、取り決め内容の承認・合意やContextの正式化を意味しない。

## 実行ゲート

### 1. 明示指定を揃える

最初に以下の3点を確認する。既存の会話に明示指定があれば利用できるが、対象が曖昧なときは確認する。

| 必須指定 | 必要な内容 |
| --- | --- |
| Work | 作業対象となる開始済みWorkフォルダのパス |
| 入力 | 使用するファイル・フォルダと範囲、または使用する回答・会話の特定箇所 |
| 出力 | Work内の保存先、作成する成果物・形式。追記・更新なら対象ファイル・箇所・許可 |

一つでも未指定・曖昧なら、作成・更新を開始せず不足している指定だけを利用者へ尋ねて停止する。Work、入力、出力を推測せず、添付資料、開いているファイル、最新のWork、サンプルや既定出力先で代用しない。

この段階では仮ファイル、雛形、JSON、ログ、フォルダも作らず、Workの記録も更新しない。

案内例（入力・出力が未指定の場合）:

```text
成果物はまだ作成しません。次を指定してください。
- 入力: 使用する資料と範囲、または使用する回答
- 出力: 指定Work内の保存先、成果物と形式
```

指定例（パス・資料名は架空）:

```text
$syncloop-arrange-project-conditions
Work: 04_WK_作業/W-0012_移行条件整理
入力: このWorkの入力一覧に登録済みの WI-001（提案書v2の移行章）と WI-002（部門回答2026-09-30）
出力: このWork直下に受託条件明細_本文案.mdと取り決めレビュー.mdをMarkdownで新規作成
```

### 2. Workと入出力の有効性を確認する

1. 案件の `AGENTS.md`、`.agents/policies/project-record-updates.md`、`.agents/policies/workspace-structure.md` を読む。
2. 指定Workの `作業内容.md`、`入力/入力一覧.md`、`作業メモ.md`、`反映候補.md` を読み、Work ID、対象TODO、開始済みの状態、目的・完了条件を特定する。必要な登録情報がない、終了済み、または作業可能な状態を確認できない場合は停止し、Workの確認を促す。Workの新規作成・開始・再開は代行しない。
3. 明示入力がWorkの入力一覧に登録され、元資料、版・時点、今回使う範囲を特定できるか確認する。外部資料の登録済み `reference` は利用できる。入力一覧全体の登録だけでは利用者が全入力を選択したことにはしない。
4. 未登録・差替えの資料や新しい回答は自動採用せず、案件の入力登録手順による登録を促して停止する。登録されるまで資料の抽出、コピー、回答スナップショットの作成をしない。他Skillを自動呼出ししない。
5. 相対パスは指定Workを基準に解決する。本文案・レビュー双方の実際の出力先が指定Work内であることを確認し、親フォルダ参照やリンク経由でWork外に出る場合も拒否する。両者の出力先は別にし、入力資料、原本、正式成果物、Workの管理ファイルを出力先にしない。1ファイルにまとめる明示指定の場合だけ同一ファイルとする。
6. 指定出力先が既存ファイルなら、無断上書きしない。利用者が対象と更新操作を明示していれば同じ許可を再度求めず、未指定の場合だけ新規パスまたは更新許可を求める。指定のない補助ファイル・JSON・ログは作らない。
7. 実行対象、入力WI-IDと版・範囲、出力ファイル・形式、Workの記録更新、変更しない領域を短く提示する。ゲート成立後は `作業メモ.md` への実績追記、必要な `反映候補.md` の候補記録、実績に基づくTODO更新を案件Policyに従って行う。これらはWork運用上の記録であり、未指定のレビュー成果物を増やす許可ではない。

指定された資料を参照できない、範囲が不明、出力が無効の場合も、書込みせず問題のある指定の修正を促す。入力・出力が有効でも、案件内容そのものの不足や矛盾は後述のレビュー対象として扱う。

## 整理・レビュー手順

1. 利用者の立場（発注・受注・内製）、今回扱う作業単位、期間、判断が必要な点を確認する。不明点は未確認として残す。契約がない内製案件に契約形態・検収を必須にしない。
2. [取り決め項目と質問](./references/取り決め項目と質問.md)を読み、9分類で明示入力の事実・候補・不足・競合を抽出する。入力外の情報を検索して補完しない。追加資料が必要なら理由と指定・登録してほしい範囲を示す。
3. 項目にWork内で一意の `PC-001` 形式のローカルIDを付ける。案件の正本IDではなく、既存項目のIDは再生成でも保持する。対象外にも理由・根拠を付ける。
4. [整合性チェック規則](./references/整合性チェック規則.md)のCC-01からCC-15を適用可否付きで実施する。項目間と入力資料間を突き合わせ、資料不足は「要確認」、不一致は「競合」とする。判定不能を整合扱いせず、一方の値を無断採用しない。
5. 未決事項にWork内で一意の `OI-001` 形式のローカルIDを付け、関連PC-ID、根拠、影響、確認先、期限、具体的な確認質問・次の行動を記録する。担当・期限が不明なら未確認とし、勝手に割り当てない。
6. [本文案の構成と作成ルール](./references/本文案の構成と作成ルール.md)と [受託条件明細書テンプレート](./assets/受託条件明細書テンプレート.md) を読み、表紙・別表1〜8へ整理した条件を記入して、本文案を指定先へ出力する。内訳業務・工程・作業・成果物ごとに行を追加し、既知の範囲は具体的に書く。記入案内の `{{...}}` を残さず、未確定・競合はOI-ID付きで表示する。情報不足を理由に本文全体を空の雛形や指摘一覧にしない。対象外の節の扱いは作成ルールに従う。
7. 別の指定先にレビュー結果を出力する。入力資料一覧、PC-IDごとの根拠・状態、CC-01からCC-15、未決事項、本文の節とPC/OI-IDの対応、変更履歴を含める。[レビュー出力例](./references/レビュー出力例.md)は構成の参考であり、案件の値を埋める入力ではない。本文だけを整えて根拠や競合を落とさない。
8. 本文とレビューを突き合わせ、対象・担当・成果物・日付・候補・未合意表示が一致するか確認する。作成ルールの出力検査で別表・小節・表の記入漏れ、プレースホルダー残り、表の崩れも確認する。レビューで未確認・競合の項目を本文で確定しない。本文の候補文はレビューにも理由と採否未定の状態を残す。
9. 利用者へ本文案とレビュー結果の保存先をそれぞれ示し、重要な未決事項・競合・必要な専門確認を報告する。不足や矛盾が残る本文案・レビューは作成できるが、取り決め完了・合意済み・顧客提示可能とは表示しない。
10. Workの作業メモに対象TODO、入力・版・範囲、結果、根拠、未決事項、次の対応をまとめる。正式反映の候補があれば `反映候補.md` にPolicy所定のID・根拠を残し、候補なしなら作業メモに「なし」と記録する。人の決定がないAI案を意思決定候補にしない。
11. 案件の `AGENTS.md` に従って `.tools/project_workflow_check.py check --strict` を実行し、検査結果、作成・更新したファイル、更新しなかった領域、残る未確認事項を報告する。検査失敗は報告し、無関係な台帳・正本を推測で修正しない。

## 項目に保持する情報

| 情報 | 記録方法 |
| --- | --- |
| ID・分類・名称・内容 | PC-ID、9分類、今回の具体的な条件。候補には理由・仮定を付ける |
| 確度 | `confirmed`（事実）、`candidate`（提案・解釈）、`unknown`（不足）、`conflict`（不一致）。根拠なく昇格しない |
| 適用 | 対象、対象外、未確認。対象外の理由・根拠を記録する |
| 根拠 | WI-ID、資料名、版・日付、章・ページ・表・回答箇所。双方の競合根拠を保持する |
| 確認 | 確認者・確認日。不明なら未確認。資料の存在確認と内容の採用を混同しない |
| 承認 | 未承認、承認済み、不要。承認者・日付・対象内容・記録、不要の理由 |
| 合意 | 未合意、合意済み、不要。必要な関係者・日付・対象内容・記録、不要の理由 |
| 未決 | OI-ID、影響、確認先、期限、次の行動 |

これはWork内の整理用であり、Context正本の4状態軸への自動変換ではない。社内承認と相手方・関係部門との合意を分け、片方からもう片方を推定しない。

## 再実行・更新

- 再実行でもWork・入力・出力を確認する。前回と同じ対象が明示されていれば再利用できるが、新しい添付や最新資料へ自動で切り替えない。
- 指定された既存本文案・レビューを読み、人が修正した内容、ID、対象外の理由、承認・合意記録を保全する。参照する既存成果物も入力として明示指定・登録されていることを確認する。
- 項目ごとに旧内容、新内容、変更根拠、影響する項目・期限・成果物、再確認・再合意の要否を示す。
- 本文案・レビューの双方で同じ変更を反映する。一方の出力先や更新許可だけが指定された場合は、関連するもう一方の更新要否・対象を確認する。
- 内容変更前の承認・合意は履歴として保持し、変更後の内容へ自動継承しない。変更範囲は未承認・未合意に戻し、無関係な項目は変更しない。
- 関係者の判断が記録された場合だけ該当内容を更新し、Work外の正本への反映やWork終了へ自動遷移しない。

## 対象外・停止条件

- 入出力指定・Work・登録入力・更新許可が不十分なら開始前に止め、ファイル・フォルダ・Work記録を作成・更新しない。
- 担当、条件、期限、契約形態、承認・合意が未確認でも、有効な入出力があればレビューは継続できる。該当項目の確定・合意済み扱いだけを止める。
- 追加費用負担、免責、性能非保証、無指摘による検収、文書の優先順位を標準条件として自動採用しない。法務・調達などの専門確認先を示す。
- Excelファイル、締結用契約書、図・画像の生成・編集、定型条文の自動適用、代理承認・代理合意は扱わない。Excel様式に沿った受託条件明細書のMarkdown表・本文案の生成・編集は対象に含む。構成図・体制図・線表に相当する情報は表へ整理し、指定入力の図を参照する場合は版・箇所を特定する。
- 原本・入力、Context正本、正式な意思決定・リスク・課題・Knowledge、Work・依頼の終了状態、アーカイブを変更しない。必要ならWork内に候補として残す。
