# 改善台帳

Flowシステムの動作確認で得た気づき・課題・問題を積み上げる台帳。社内システム開発を例題として各Skill・Policy・検査を動かし、その結果をここに記録する。

## 記載ルール

- 1件につき1つの見出しを追加する。見出しは `## IMP-連番 件名` とし、連番は3桁で振り直さない。
- 新しい件は末尾に追記する。既存の件を更新するときは本文を書き換え、経緯は「記録」に日付付きで追記する。
- 各件は次の項目を本文の後の箇条書きで持つ。
  - 日付: 気づいた日（YYYY-MM-DD）
  - 対象: 該当するSkill・Policy・検査・テンプレートなど
  - 事象: 何が起きたか、再現手順
  - 影響: 誰の何が困るか
  - 改善案: どう直すとよいか（未定なら「未定」）
  - 状態: 未着手 / 検討中 / 対応済み / 見送り
  - 記録: 日付付きの経緯
- 事実・推測・未確認事項を区別して書く。

## IMP-010 WBS（長期）と進行計画（直近）を別ファイルに分けたい

現行の進行計画は、依頼全体の作業分解（WBS）と、直近に何をどの順で始めるかを1つの表にまとめている。はやてさんの意図は次のとおり（2026-10-08の発言の要約）。WBSを作る目的は、長期の案件でWorkを積み上げるだけだと全体の位置が分からなくなるのを防ぐこと。そのため、WBSは複数のWorkを束ねる長期の計画として別ファイルにし、進行計画には「とりあえずここまで」という直近の計画を書きたい。

RQ-0001（ダミー案件）を例に、現行のSkill・テンプレートには合わせずに見本を2つ作った。

- [RQ-0001_WBS.md](提案/WBSと進行計画の分離/RQ-0001_WBS.md): 依頼の終了までを見渡すガントチャートと作業パッケージの表。1行が複数のWorkを束ね、「紐づくWork」にW-IDを追記していく。更新は作業パッケージの増減・完了条件の変更・Workの紐づけ時だけにする。
- [RQ-0001_進行計画.md](提案/WBSと進行計画の分離/RQ-0001_進行計画.md): 次の区切り（判断ゲートや打ち合わせ）までの計画。WBSのどこを進めるか、どのWorkをどの順で始めるかを書き、区切りに着いたら書き直す。

見本を作ってみて分かった論点（AIの推論を含む）:

- 良い点: WBSは変化が少なく、進行計画は区切りごとに書き直すため、更新の頻度と目的が分かれる。部分計画の「未計画の範囲」を別表で持つ必要がなくなり、WBSの粗い行がその役を兼ねる。
- 懸念: W-IDをWBSと進行計画の両方に書くため、二重管理になる。どちらかを正本にする必要がある（案: W-IDの正本はWBS、進行計画は「予定」までを持ち、開始後はWBSを見る）。
- 未決: 計画項目のIDをWBS IDだけにするか、P-IDを残すか。Work Startが参照するIDと、終了同期が読む表を合わせて決める必要がある（IMP-009と関係）。
- 未決: 区切りごとの進行計画の承認を、依頼全体のPlan承認と同じ重さにするか。軽くしないと、区切りのたびに承認の手間が増える。
- 未決: ガントチャートを描くには日付が必要だが、判断ゲート前は根拠のある日付がない。仮置きの日付をどう区別し、誰が承認するか（見本では「（仮）」を付けた）。
- 未決: ガントチャートの表示先。Mermaidは GitHub 上では図として表示されるが、エディタやツールによっては表示されない。

- 日付: 2026-10-08
- 対象: syncloop-flow-request-plan、assets/進行計画.md、syncloop-flow-work-start、.tools/project_workflow_check.py、.tools/work_close_gate.py、使い方.md
- 事象: RQ-0001のPlanで、WBSと直近の計画が1つの表に混ざっていることに利用者が違和感を持った。
- 影響: 長期の案件では、1つの表が全体の見通しと直近の段取りを兼ねるため、更新のたびに全体を書き換えることになり、どちらの役にも中途半端になる（推測）。
